## 1 같은 건물을 선택하고 화면 익히기

운영 주소: https://roaring-maamoul-d1bbf1.netlify.app/

| 화면 | 하는 일 |
| --- | --- |
| 공간 분석 | 구조물·관계·점검 순위·사례 검증 |
| GIS 입지 | BIM 좌표와 지리 좌표 기준 연결 |
| 역할 체험 | 같은 구조물의 로컬 데모 |
| 공동 관리 | 계정별 실제 요청·점검·상태 공유 |
| 개인 백업 | 내 계정에 스냅샷 저장·복원 |

1. 기본 화면은 가상 공동주택 84개 구조물이다. 구조물을 클릭하거나 선택 목록에서 ID를 고른다.
2. 3D를 드래그해 회전하고 휠로 확대한다. 층 버튼으로 층을 선택한다.
3. 자재·시공·점검 기록에서 건물 ID와 구조물 ID를 확인한다.
4. 모바일은 메뉴 버튼으로 분석 메뉴를 펼친다.

역할 체험 버튼은 실제 권한이 아니다. 실제 공동 관리는 로그인과 서버의 건물 멤버십이 필요하다. 개인 백업은 자동 저장이 아니며 저장 버튼을 눌러야 한다.

## 2 공개 IFC와 자재 확인

1. 사용 가이드에서 Duplex 샘플 JSON을 내려받는다.
2. 기존 모델이 필요하면 먼저 모델 JSON으로 내보낸다.
3. 모델 가져오기에서 파일을 선택하고 파일 읽기·검사를 누른다.
4. 객체 50개·가상 결함 25건을 확인하고 검사한 모델로 교체한다.
5. IFC 메시 우선 표시와 분석 경계상자 표시를 전환한다.
6. 구조물에서 IFC GlobalId·층·자재와 연결 관계를 확인한다.

Duplex는 공개 IFC의 삼각형 메시·층·자재와 가상 Q/M/E·결함을 결합했다. 직접 원본 IFC 가져오기는 단순 압출만 지원하므로 복잡한 Duplex는 변환 JSON을 사용한다.

자재·검사 지표 편집에서 자재·규격·시공일·검사일·Q/M/E를 저장한다. 역할 체험의 자재 목록은 같은 구조물 데이터를 사용한다. 자재 라이브러리에서 편집은 공간 분석의 해당 구조물로 연결된다.

모델을 바꾸면 다른 건물의 관리 이력은 분리 보존한다. 현재 모델에서 찾을 수 없는 기존 ID는 미연결로 표시하며 임의로 다른 객체에 연결하지 않는다. 다른 탭의 폼을 편집 중이면 모델 변경 안내 후 새로고침한다.

메시는 시각화에 사용하고 공간 관계 계산은 AABB를 사용한다. 실제 검사·시공 품질·안전 판정은 별도 검증이 필요하다.

## 3 GIS·관계·검증 결과 비교

GIS 입지에서 투영좌표계(EPSG:3857/5186), 원점 Easting/Northing, 회전·축척·높이와 출처를 입력해 저장한다. 경위도를 원점으로 변환할 수 있다. Duplex IfcSite 위치는 참고값이며 실제 측량 배치로 인증되지 않는다.

외부 WGS84 면 GeoJSON과 출처·기준일을 연결하면 경계상자 중첩 후보를 본다. 정밀 교차·침수 위험 판정이 아니다. 지도 좌표의 건물 경계를 GeoJSON으로 내보낼 수 있다.

1. 공간 관계 분석에서 인접 거리와 배관 탐색 단계를 설정한다. 기본값은 0.35m·1단계다.
2. 점검 우선순위에서 Q/M/D/E와 가중치 30/25/25/20을 비교한다.
3. 분석 비교·연구 검증에서 사례 JSON 양식을 내려받는다.
4. 같은 건물의 source·reviewer·reviewedAt, anchorId·evaluatedIds·confirmedIds를 채운다. 실제 사례가 없으면 synthetic을 유지한다.
5. 사례를 가져와 검토한 대상 범위에서 두 방법의 Precision·Recall을 비교하고 결과 JSON을 내보낸다.

미검토 구조물을 정상으로 간주하지 않는다. 출처 정보는 사용자 선언으로 진위를 자동 인증하지 않는다. 기본 합성 점수는 안전 등급·고장 확률이 아니다. EPSG:3857 지도 거리에는 왜곡이 있어 내부 거리 분석에 사용하지 않는다.

## 4 실제 계정으로 공동 요청 처리

최초 한 번은 Firebase 프로젝트 소유자가 계정 신원을 확인한 뒤 시스템 관리자 UID를 등록해야 한다. 사이트의 공동 관리 → 자세한 설정·검증 현황을 따른다.

1. 개인 백업에서 본인의 SPATIA 계정을 만들거나 로그인한다.
2. 공동 관리에서 같은 계정으로 로그인해 UID를 확인한다.
3. 프로젝트 소유자는 Firestore systemAdmins/{UID} 문서를 콘솔에 등록한다. 웹 사용자는 스스로 생성할 수 없다.
4. 시스템 관리자는 forest-a-demo 또는 현재 모델의 건물 ID를 열고 구조물을 등록한다.
5. 멤버십 등록에서 담당자의 UID·역할·세대(예: 302)를 지정한다.
6. 입주자는 담당 건물을 열어 등록된 본인 세대/공용부 구조물을 선택하고 요청 제목·설명을 등록한다.
7. 관리자는 전문가 UID·처리 상태·다음 조치 예정일을 저장한다.
8. 입주자는 실시간 상태를 확인하고 보수 완료 후 확인 완료를 저장한다.

서버가 성공한 경우에만 저장 완료를 표시한다. 오류 시 로컬 저장으로 대체하지 않는다. 사진과 개인 연락처는 공동 관리에서 수집하지 않는다.

역할 체험의 요청은 브라우저 데모이며 자동으로 공동 관리에 업로드하지 않는다. 개인 백업도 별도 명시적 스냅샷이다.

## 5 전문가 검토와 승인 설명

1. 전문가는 공동 관리에서 배정된 요청을 열고 비공개 점검 기록 작성을 누른다.
2. 전문가 원문·쉬운 설명·다음 조치와 예정일을 작성한다.
3. 직접 검토했음을 표시하고 비공개 서버 저장을 누른다.
4. 관리자는 검토된 기록을 확인해 현재 검토본 공개 승인을 누른다.
5. 해당 입주자는 본인 세대와 공용부의 승인된 설명을 조회한다.

공개 문서에는 전문가 원문이 포함되지 않는다. 승인한 개정의 사본을 공개하며 이후 원문 수정은 자동 공개되지 않는다. 다른 세대나 미배정 계정의 조회는 서버가 거부한다.

AI 모델은 연결하지 않았다. 역할 체험의 설명 초안은 용어 사전 기반이다. 전문가가 현장 상황과 대조하고 미확정 사항을 유지해야 한다.

운영 Firebase에서 임시 계정으로 개인 백업·공동 요청 저장, 다른 UID·세대의 접근 차단, 실시간 상태와 승인 설명을 검증했다. 이는 실제 건물의 안전·현장 정확도 인증이 아니다. 임시 테스트 계정·기록은 정리했다.

실제 사용할 멤버십은 임의로 부여하지 않았다. 로그인 후 UID를 확인해 프로젝트 소유자가 최초 권한을 등록해야 한다. 상세 절차와 검사 범위는 사이트의 권한 설정·검증 현황에서 확인한다.
